# Validation record

Routine tests use deterministic offline wallets. Network funding and transactions run only in separately authorized trials. The current checks used Apple Silicon, Rust 1.99.0 for Mesh and Rust 1.95.0 for Tempo.

## Long-lived payment channels, 2026-11-24

Payments changed from one native reserve per request to one long-lived channel per buyer and seller, with concurrent requests per pair, Lightning-style buyer configuration, standing and strikes, ledger settings, the new `control` commands and journaled wallet sends. This change has offline validation only. Every dated section below describes the earlier per-request design and its APIs.

Formatting, `cargo check` and Clippy with warnings denied, `cargo test --locked --all-features` (155 library tests, one harness test and six process tests) and rustdoc with warnings denied passed. The engine tests run with a configuration that passes startup validation. The tests cover:

- the seller admitting the voucher it already stores without a chain call, while a new or higher one is verified;
- top-ups only when a voucher would not fit, a concurrent bill waiting for a pending top-up, and the refusal before dispatch when one top-up could not pay the worst case;
- requests with different bodies running at once on one channel, a later bill held until the earlier one, a bill between another request's quote and voucher, also when it overtakes the quote, bills of concurrent requests paid beyond the daily budget, and two first requests opening one channel with the second at upfront 0;

Validation used clean Mesh `14bb8f4f1ee5d0463fa3b1ef06a780e640a9566c` on branch `peer-evidence` and the Tempo working copy based on `f7f8c963ee41677d15a355106c639ff06fecff9a`. Buyers apply bond policy to the seller they select; sellers choose their workers. Each relay with a configured verifier applies its local policy to provider gossip. Policy-only verdicts last until verifier restart or eviction; bond-state checks and transient failures retain finite deadlines. Mesh checks the selected seller's cached bond eligibility before payment callbacks, without another bond-verification call. Paid callbacks still perform payment RPCs. The [bond guide](bonds.md) describes validity and exit semantics.

## Previous API cleanup, 2026-11-19 (superseded)

At this earlier validation point, the uncommitted cleanup removed the two evidence lookup RPCs and the optional provider-filter switch. An empty evidence grant table requires provider verification; initialization reports grant presence, node identity uses the existing identity API, and Tempo tracks mesh ID from snapshots/events. Only local publication remains an evidence host RPC. Tempo’s provider policy is always applied when bonds are enabled; publication-only mode is removed. Mesh still initiates verification and owns the eligibility cache; admission performs no evidence lookup.

Focused fast tests passed: 289 Mesh configuration tests, three SDK contract/compatibility tests, three host initialization tests, 13 host evidence/cache and loopback gossip tests, four Tempo runtime tests, three provider-policy tests, eight native bond fixture tests, two harness tests and six Tempo process tests. The process tests cover early configuration rejection and mesh-ID snapshot updates and clearing without a host lookup. Mesh and Tempo also passed incremental checks and Clippy with warnings denied. Configuration, SDK and Tempo rustdoc passed with warnings denied; host rustdoc completed with its 14 existing private-link warnings. Validation used an isolated Cargo manifest referencing the working-copy source and local SDK, preserving the repository's immutable dependency pin and lockfile. The uncommitted SDK API requires this local override until a new SDK revision is committed and pinned.

Full suites, product/package builds and testnet trials were deliberately deferred for this cleanup. The complete validation and Moderato evidence below describe the preceding tested source, not this uncommitted API change.

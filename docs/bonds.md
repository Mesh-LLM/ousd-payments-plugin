# Refundable Tempo bonds

The running `tempo` process provides payments and bonds through one wallet, signer, journal and nonce stream when the node has a wallet. A node without one verifies other providers' bonds with only its RPC and serves free inference; it cannot pay, charge or post a bond. Sellers may configure prices, publish a bond, do both or do neither. Buyers may use free inference, explicitly authorize paid inference within spending limits and independently require a minimum provider bond. No price means free inference. Without a bond requirement, Tempo applies no bond-based filtering; fresh signed supply and normal Mesh discovery still apply. Starting the plugin never signs a new bond transaction. It reconciles and can rebroadcast previously signed attempts, and resumes outstanding payments under existing authorizations.

A deposit binds one funding wallet, Mesh mesh ID and host public key. Another host or mesh needs its own deposit. The escrow has no administrator, seizure, slashing, fee recipient or upgrade proxy. Funds stay locked indefinitely. Only the funding wallet can request exit, which starts the fixed exit delay chosen at deposit, and reclaim the full principal after that delay. The bond remains eligible during the exit countdown and stops qualifying when withdrawal becomes possible, even if its owner has not submitted the withdrawal transaction. Gas is paid separately in OUSD. There is no renewal, periodic refresh transaction, exit cancellation or delay change.

## Host integration

Use the full companion Mesh branch `peer-evidence`. Tempo's pinned SDK supplies the interface, and the full host branch supplies enforcement. Tempo requires `peer_evidence.v1` at initialization. A node with a wallet needs a persistent Mesh identity, including an explicit `MESH_LLM_NODE_KEY_PATH` for a client-only buyer: its payment ledger and bond are bound to the node identity and must survive restarts. A node without a wallet pins nothing, so a buyer that only verifies bonds can keep the client's default identity. Use separate key paths and Tempo state directories for public and private operation: switching modes rotates the selected node key, including an explicitly configured path.

Install a Tempo package declaring its verifier. Mesh makes selected verifier packages required and eager, and validates their packaged declarations before accepting peers. Its authenticated live manifest must agree with contract version 1, namespace `tempo.bond.v1` and handler `verify_peer_evidence`. No evidence permission or empty grant table is needed. Unsupported or malformed declarations and conflicting namespaces fail startup. Restart Mesh after changing plugin policy so old decisions cannot outlive it. A changed published reference needs no restart: Mesh keys decisions by the evidence itself.

Tempo obtains its node identity through `ReadIdentityBundle` and subscribes to mesh-ID snapshots/events. Its local `bond_context` control reads that snapshot and the manifest namespace; `mesh_id` remains null until known and is cleared if Mesh clears its ID. New bond locks require a known mesh ID. `PublishPeerEvidence` is the only evidence host RPC, used to publish the local bond reference or withdraw it with null.

Each receiving node checks the origin-signed record before invoking its own verifier with authenticated mesh/provider identity and the evidence from the declared namespace. Mesh rejects a provider that published no evidence without asking Tempo; Tempo verifies a supplied proof against finalized escrow state, and rejects every proof on a network without a configured escrow. Buyers never need to post their own collateral.

Mesh owns the only eligibility cache and reuses decisions for gossip relay, discovery listings and routing. Its validity, retry and pruning rules are described under [Escrow and policy](#escrow-and-policy). Verification runs outside membership heartbeats. Expired or rejected decisions block provider propagation, selection, routing-table responses and new inference work while retaining bounded authentic signed records for revalidation. Relays cannot replace a held record with an older one; authenticated direct origins retain Mesh's existing restart sequence-reset behavior. After revalidation, routing uses supply from the current held signed body. Supply comes from the signed body, so relays cannot attach unsigned models to another identity. Ordinary record freshness and peer-health checks remain independent. Admission callbacks receive no bond evidence and perform no additional verification.

Tempo permits one chain verification at a time, including direct calls to its published verifier operation. Contention fails immediately and uses the configured finite failure retry. The gate stores no eligibility decisions.

Publication must also fit Mesh's total signed node record budget. Mesh rejects a reference that would overflow the current record without replacing prior evidence; reducing advertised metadata creates room. Withdrawing a reference remains allowed. Mesh orders identity snapshots and live updates and never replays an old mesh ID into a replacement plugin process.

Mesh knows namespaces, signed records, acceptance and expiry. Currency, collateral and pricing policy remain in the plugin, so a Bitcoin verifier can use the same contract. With a verifier active, Mesh requires origin-signed provider records even when Tempo accepts missing bond evidence.

Fresh authenticated direct admission alone cannot qualify unsigned provider supply for verification or reuse of a cached absent-evidence verdict. The buyer checks the seller it selects, and the seller chooses and operates its own infrastructure. Mesh does not require bonds from the workers behind that seller's local runtime. Internal stage control and transport retain their membership, topology and lifecycle authorization. Bond eligibility checks for the selected seller reuse Mesh's cache without additional verifier or blockchain calls; already admitted requests can finish.

## Escrow and policy

One escrow per network serves every mesh and provider. On Moderato the plugin uses the escrow at `0xd210B0356b3e45B37F29Ec763106dc23BF1cC3aa`, deployed from `contracts/src/TempoBondEscrow.sol` (its pinned creation bytecode is `contracts/creation.hex`); `bonds.contract` overrides it. Mainnet has no escrow yet: deploy it once with Foundry and set `bonds.contract`. The plugin never deploys it. Bond verification and explicit escrow operations check the selected chain, canonical OUSD token and exact deployed runtime bytecode, pinned in `contracts/runtime.hex`. Publication only serializes the published reference; receiving verifiers validate it when their policy requires a bond. `just contracts-check` compares both checked-in bytecode artifacts with the pinned Solidity 0.8.30 build and exercises the contract.

Example plugin settings on Moderato, in addition to `data_dir`, `wallet`, and any payment configuration:

```json
{
  "bonds": {
    "max_lock": "20000000",
    "max_exit_delay_seconds": 604800,
    "verification_retry_seconds": 60,
    "providers": {
      "minimum_amount": "10000000",
      "minimum_exit_delay_seconds": 86400
    }
  }
}
```

All amounts are millionths of OUSD on the selected network. A config that omits `bonds.providers` requires the default bond: at least 1 OUSD with an exit delay of at least the network's default. The default exit delay is one minute on testnet, so a trial bond comes back within minutes, and one day on mainnet. A requirement can be lowered but not turned off: installing the plugin always filters providers by bond. On mainnet, where no escrow is deployed, no provider qualifies until `bonds.contract` names one. When supplied, its omitted fields default to one atomic unit and no additional minimum exit delay. Explicit production requirements should set both minimums, as above. On mainnet, checking bonds or publishing one needs `bonds.contract`. Neither a requirement nor publication implies the other. A qualifying bond must be funded, unwithdrawn, bound to the expected mesh and host key, and locked against withdrawal. Amount and exit delay are independent requirements, with no amount-times-duration score. `max_lock` and `max_exit_delay_seconds` authorize explicit new deposits and default to 1 OUSD and one day; they do not create a bond.

When a requirement and proof are present, verification reads one finalized block through the locally configured RPC. It checks identity, amount, exit delay, contract and exit state. It trusts that RPC's finalized state rather than running a light client. An active bond's decision expires at that block's timestamp plus its exit delay: an exit requested immediately afterward still cannot release the principal during that window. For an exiting bond, the decision expires at its exact withdrawal deadline. A bond stops qualifying at that deadline, even while its principal remains in escrow awaiting withdrawal. There is no fixed positive polling interval. Longer exit delays safely reduce chain reads. Mesh uses the plugin's `valid_until` directly, with no core validity setting or fixed cap. Its routing and forwarding boundaries enforce expiry using local wall and monotonic clocks. Cache hits never move the original deadline.

Exit delays must be between 1 and 4,294,967,295 seconds, approximately 136 years. Withdrawal timestamps use a full-width integer so supported delays cannot overflow; public `withdraw_at` metadata is a decimal string, with `"0"` meaning no exit request. Finalized observation timestamps must lie between 120 seconds behind and 5 seconds ahead of the local clock, and their derived deadline must still be in the future. A receipt alone never establishes continued eligibility.

Mesh owns the only eligibility cache and keeps decisions only for the current evidence of current providers. A rejection on a network without a configured escrow carries a deadline a year away; a verifier restart or the provider leaving invalidates them sooner, and changed evidence uses a different key. These decisions perform no chain reads. This is independent of bond-backed deadlines derived from escrow exit delays. Its keys bind the mesh, the host key and a digest of the evidence; a provider without evidence is rejected without a cache entry or a call to Tempo. A Tempo restart discards every decision, including answers still in flight, so a changed policy cannot reuse them; other plugin restarts leave them in place. Positive decisions from gossip are reused for provider selection without invoking Tempo again. Mesh verifies from one background loop and consults the cache before each call. Tempo retains no second eligibility cache. Failed Tempo checks return a rejection deadline using `verification_retry_seconds` (default 60), which Mesh caches to avoid repeated chain reads during outages or repeated invalid proofs. Mesh wakes its existing background refresh path when a finite decision expires, without waiting for the next gossip heartbeat. Provider work stays blocked until revalidation succeeds. No event subscription, block cursor or chain monitor is implemented.

## Operator actions

A seller that posts the default bond runs two commands: `fund`, which creates the wallet and on Moderato asks the faucet for test OUSD, and then `bond_lock`. Signing a new bond lock or exit requires an explicit operator command; once an exit's delay has passed, the plugin withdraws that bond into the wallet by itself. A node that only verifies other providers' bonds needs no wallet.

While Mesh is running, the local Tempo `control` operation accepts:

- `bond_context`: read the local mesh ID, host key, manifest namespace, published bond reference and provider requirement.
- `bond_lock`, with every input optional: bind a deposit to this host and a mesh. `amount` and `exit_delay_seconds` default to 1 OUSD and the network's default exit delay, one minute on testnet and one day on mainnet. `mesh_id` defaults to the observed mesh; an explicit one that differs from it is rejected before signing, which preserves operator intent if a mesh update races the command. The 32-byte hex `salt` defaults to one derived from the mesh and host key, and `operation_id` to one derived from the salt, so repeating the command resumes the same bond instead of locking another. A second bond for the same mesh and host, for example after a withdrawal, needs its own `salt`.
- `bond_exit`, with every input optional: start the bond's exit countdown, then withdraw the principal to the wallet that funded it once the delay has passed. Eligibility lasts until the withdrawal deadline. `bond_id` defaults to the newest finalized lock, and `operation_id` to one derived from the bond, so repeating the command resumes the same exit. The exit attempt's `withdraw_after` shows when the plugin starts trying the withdrawal; it retries on each tick until the finalized chain reaches the deadline, and the node must be running for it. Once the withdrawal finalizes, the plugin withdraws the published reference.
- `bond_publish`, with an optional `bond_id`: publish that bond as this node's evidence, for example one locked before the state directory was replaced, or withdraw the reference without `bond_id`.
- `transactions` and `pending`: inspect public attempt metadata, including bond attempts. In-process `retry` without a `request_id` reconciles the shared wallet journal and resumes outstanding payments and channels under existing authorizations; it can sign payment transactions. With a `request_id`, it progresses that payment.

A seller can join the mesh, read `bond_context`, and then fund a deposit. Once the lock finalizes the plugin publishes it, without a configuration change or restart, and republishes it at every start; a newer finalized lock replaces it, and a finalized withdrawal withdraws the reference. Membership does not require a bond; buyers select the seller once its signed publication meets their own bond policy. A node can check others' bonds without a wallet. With a wallet, it may leave the wallet locked when only verifying or publishing evidence; signing a new transaction requires unlocking. Remote callers cannot use the peer-evidence hook to sign transactions.

Bond operations run only as controls on the running plugin; the CLI only initializes the wallet and reads its address. Every control that signs a new bond transaction has an operation UUID; each derives one when none is given. Equivalent UUID spellings identify the same operation. Repeating that UUID must retain identical intent; it never signs replacement bytes.

A lock has no maturity date. To release it, run `bond_exit`; once the finalized chain timestamp reaches `withdrawAt`, the plugin withdraws it. Repeating the same signed exit operation reconciles its original bytes. The contract also makes repeated exit requests idempotent, so they cannot reset or shorten the delay. Exit requests and withdrawals remain available when authorization for new locks is zero. No background task initiates a new exit or signs replacement bytes merely because the wallet exists; the only bond transaction the plugin signs by itself is the withdrawal of a bond whose exit this wallet requested. The wallet skips reconciliation RPCs when its shared journal has no pending transaction.

Deposits use native Tempo multicall to approve exactly the bond amount and lock it atomically. Payment, wallet send, deposit, exit and refund attempts share one journal, send mutex and unresolved-transaction gate. Signed bytes commit before broadcast. Receipt finality and expiry use the same finalized block cutoff. If a receipt is missing after expiry but the nonce was consumed at that cutoff, the attempt stays pending until its receipt can be resolved. Restarting, removing prices or removing authorization for new locks cannot release an uncertain nonce or replace its transaction.

## Validation

Routine tests use deterministic local wallets, RPC fixtures and plugin-process fixtures. The host smoke additionally runs two real Mesh nodes. The explicit `just testnet-bonds MESH_BINARY FRESH_PRIVATE_DIRECTORY` workflow creates fresh testnet wallets, requests faucet coins, uses the Moderato escrow, or the one named by `TEMPO_BOND_ESCROW`, and exercises paid/free inference, provider filtering, delayed exit and refunds. It requires a `host-smoke` harness from `just build` and uses the adjacent debug `tempo` binary. The [latest validation record](validation.md#current-mesh-compatibility-2026-11-21) records a completed trial against the current companion host and plugin. It uses 30-second exit delays and a 1-second failure retry; production retries default to 60 seconds. The backend returns canned usage, so the trial validates integration and settlement rather than model quality.

The [earlier maturity-and-renewal trial](tempo-bonds-testnet-trial.md) used a different contract. Its address and runtime are historical. This exit-delay contract requires a fresh trial directory. The harness saves the escrow address and the lock, exit and refund inputs before submission and reuses them on resume. A saved checkpoint resumes at exit/refund processing after positive admission tests; release waits on finalized chain time. A terminally failed signed operation needs inspection; resuming never silently creates another deposit. Contract tests cover indefinite locks, exit ownership and exact delay boundaries, idempotent exit requests and full principal refunds. The [earlier exit-delay trial](tempo-exit-testnet-trial.md) records the preceding host/plugin API; current results are in the latest validation record.

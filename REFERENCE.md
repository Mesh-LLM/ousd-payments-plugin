# Architecture

Payments Plugin is one Cargo package with one production executable, `tempo`. Mesh supplies inference lifecycle events, authenticated peer transport, and request identity. Payment and bond policy, chain verification, signing and wallet state stay inside the plugin process. Mesh carries origin-signed opaque provider evidence and owns one eligibility cache. It invokes the namespace-restricted verifier on a cache miss and enforces provider eligibility for gossip relay, discovery listings and routing. Mesh refuses a verifier that starts lazily, runs at most one verifier, and registers it before accepting peers, without evidence permission plumbing. Mesh rejects a provider without evidence before asking Tempo. An omitted provider requirement means the network's standard bond; on a network without a configured escrow no bond qualifies. Pricing, paid buying and seller bond publication are independent. Existing identity reads and mesh-ID snapshots supply local context; the sole evidence host RPC publishes or withdraws the local reference. Evidence stays out of admission callbacks. Rejections without a configured escrow carry a deadline a year away, so Mesh keeps them until the verifier restarts or the provider or its evidence changes; bond-state checks and transient failures have nearer deadlines. Mesh caps any verdict at one year. Membership heartbeats never wait for bond verification. Bond-lock controls require the intended mesh ID explicitly and reject an observed mismatch before signing.

```text
Mesh lifecycle and peer messages
    |
    +-- tempo
          engine + ledger
              |
              +-- typed wallet calls
                    Tempo wallet + journal + keys + RPC verification
```

| Module | Ownership |
| --- | --- |
| `bonds` | Opaque bond references, independent amount/exit-delay policies and stateless finalized escrow verification with deadlines for the Mesh cache. |
| `tempo::bonds` | Atomic deposits, delayed exits, refunds and durable transaction recovery. |
| `tempo::transaction` | Shared native signing and exact-byte retries for payments, sends and bonds. |
| `tempo::send` | Journaled OUSD transfers out of the wallet's own balance. |
| `runtime` | Plugin registration, startup, host callbacks, and ordered per-peer message handling. |
| `control` | The `control` operation: payment controls named as in the Lightning plugin, wallet sends, recovery and bond commands. |
| `engine`, `engine_admission`, `engine_mpp`, `engine_seller`, `engine_serving` | Request agreements, the buyer's admission wait, bills, the seller's standing and strikes, peer coordination, and recovery for buyers and sellers. |
| `engine_bonds` | The published bond reference: set when a lock finalizes or by the operator, withdrawn with its bond, and repeated until the host accepts it. |
| `engine_channel` | The channel lifecycle: buyer open, top-up and recovery; seller watch, idle and unpaid-bill closes. |
| `protocol`, `contract` | Peer messages, channel and request terms, vouchers, bills, closures, and exact amount serialization. |
| `ledger`, `ledger_settings` | Requests, channels, daily spending, node and wallet pins, runtime settings (policy, prices, admission deposits), and atomic database updates. |
| `tempo::wallet`, `tempo::journal`, `tempo::keys` | Local signing policy, channel operations, nonce ownership, signed transaction persistence, encrypted keys, and exclusive wallet ownership. |
| `tempo::rpc`, `tempo::receipt` | Tempo RPC, native ABI, vouchers, and independent finalized evidence checks. |
| `request_stream` | Bounded request-body receipts required by the pinned host lifecycle. |
| `wallet` | The small typed backend interface used by the native wallet and deterministic fixtures. |

The engine calls its wallet directly with typed Rust values. There is no wallet provider capability, operation binding, serialization boundary, child process, or separately installed wallet. The backend interface permits deterministic tests without weakening production startup: only the separate, feature-gated fixture executable can load fabricated wallet evidence.

Authenticated membership and payment control messages remain available independently of provider eligibility. Inference routing requires a current provider verdict. A verifier disconnect, restart or shutdown discards its decisions and withdraws its publication. Projection also checks that the signed record is still current after asynchronous policy checks.

The engine ledger and wallet journal are separate tables in one SQLite database in `data_dir`, beside the encrypted key. They represent different facts: requests, channels, spending and settings versus signed transactions and nonces. Writes are durable, and one exclusive lock gives a single process ownership of the key, nonces and state. A change to a request and its channel, such as a voucher with its daily spending or a channel close with its requests, commits in one transaction. Payments, sends and bonds share the signed transaction representation and pending-transaction reconciliation. Internal journal reads stay typed; public attempt output removes signed bytes. Idle wallet reconciliation performs no chain reads. Restart recovery reuses original identities and signed bytes; missing usage never becomes a measured zero charge. A request holds its pair's slot for its body, so identical bodies run one at a time; a request with unknown usage stays open for audit without holding it. The seller never bills it once it has told the buyer so, which the buyer acknowledges, or once a later request on the pair is quoted. Each role has its own slots per peer. This is new code with no compatibility or migration layer for earlier versions; the ledger refuses an older schema.

Startup writes the configured policy, seller prices and a set admission deposit into the ledger settings, as the Lightning plugin does; the engine reads them from there, and controls change them at runtime. Every start re-applies the configured policy and prices, so a runtime switch to `free_only` or a price removed at runtime reverts at the next start unless the configuration file changes too. Startup does not remove ledger prices for models missing from the configuration. Each priced model is registered with the host as requiring the payment channel; changing a price re-registers it, and an unpriced or free model has the requirement withdrawn. One engine lock serializes each settings change with its host call, so host calls follow ledger order, and a host call that fails is repeated on the next reconciliation tick.

The supported asset is six-decimal Open USD at `0x20c0000000000000000000006a37da5c996874be` on either Tempo network. `wallet.network` selects `testnet` (Moderato, chain 42431, default RPC `https://rpc.moderato.tempo.xyz`) or `mainnet` (chain 4217, default RPC `https://rpc.tempo.xyz`). Testnet is the default. A custom `wallet.rpc_url` does not change the selected network. For payments, both peers must use the same network and have an unlocked wallet funded for gas. Payment and gas use OUSD on that network.

The wallet profile and the database's wallet pin bind their chain. Use a separate `data_dir` per network. Channel salts include the asset chain ID, and channel IDs, transaction signatures, and EIP-712 vouchers use the selected chain. Wallet calls reject another network's terms before querying or resuming transactions.

The buyer's voucher authorizes the channel's running total of acknowledged bills plus any unused upfront credit. The seller alone chooses the capture when it closes; the plugin captures the billed total up to the best voucher, but chain enforcement only bounds the capture by the voucher. The upfront is the voucher increase over the seller's view that the seller requires before work. The buyer accepts it only while the seller's unbilled credit, the voucher minus the bills, stays within the buyer's `admission_deposit`: a new channel can get a full upfront and later upfronts can only refill credit to that limit, never stack. A seller that bills a request the buyer refuses, or overstates usage, can therefore keep at most that credit plus the bills the buyer signed. The buyer records an error when a close captures more than the bills it acknowledged. Bills beyond the credit need the buyer's own matching usage observation before it signs. Vouchers never prove computation.

Standing follows the Lightning plugin. Once a seller admits a newly verified nonzero voucher from a buyer, the buyer has standing: later requests, and the first request on a new channel, need no upfront, so such a channel opens with a zero voucher. Standing lives in memory, for at most 1,024 buyers; the set is cleared when full and at restart. The seller answers `Busy` while the buyer has three unpaid bills: bills on its open channel above the best voucher, and bills on a closed channel that neither its capture nor the seller's best voucher covered, which count until the operator runs `unblock`. Running requests never count, nor does usage that arrives after a channel began closing, which is never billed. Requests run at once, so a buyer with standing can leave many bills unpaid before it reaches three; as in the Lightning plugin, nothing else bounds that exposure.

Before dispatch, the buyer refuses a request unless its upfront plus the voucher increase a worst-case bill would need fits `cap` and the remaining daily budget. One top-up must also be able to pay its worst-case bill. The buyer tops up when a bill's voucher would exceed the deposit, once per bill, and later bills on the channel wait for it. The top-up must finalize within the seller's 120-second payment time, which a busy wallet transaction slot can delay. Concurrent requests may overshoot the daily budget by their bills, as in the Lightning plugin. The worst case counts every byte of the canonical request body as an input token, plus the full output limit. The seller admits the forwarded request only if its body digest equals the agreed one, which binds that bound to the request that runs. The seller caps every bill at that worst case, and at bill time the buyer refuses a bill above it and checks the cap again; neither the daily budget nor a switch to `free_only` stops paying for work already dispatched. Byte counting only approximates the prompt's token bound: a default system prompt or a tokenizer could produce more tokens than the body has bytes. The seller absorbs that difference, so an honest bill is never refused for it.

A seller may be behind the buyer's latest voucher, for example after a lost message. The buyer accepts a quote whose voucher is at or below its own, with its channel and payee, and no more bills than its own accepted total plus what its other requests may still be billed; fewer is fine, since a bill may be on its way or may have overtaken the quote; it resends its latest voucher; only increases above its own count against the budget. A seller that never received the first voucher quotes no channel; while the buyer's channel has no bills, the buyer accepts that and sends the existing channel with its voucher. Bills are numbered per channel, and a bill that overtakes an earlier one waits for it. A quote showing a higher voucher than the buyer signed, or other bills, makes the buyer recover the channel.

The seller never calls `settle`, so everything a channel has earned stays at risk until the seller's close finalizes, not just the latest bill. After a buyer's close request, a seller or its RPC that is unavailable for the whole 900-second grace loses every voucher on that channel: `withdraw` refunds the deposit minus the settled amount, which is zero, and deletes the channel. The seller then records the earned and captured amounts as a channel error. Because an active channel closes only after an hour without requests, the amount at risk grows with the channel's lifetime, bounded by its deposit. A later mitigation is a threshold settle that claims when the voucher exceeds the settled amount by a limit. It would bound the loss to unsettled earnings, at one transaction and one turn of the wallet's transaction slot per settle.

Both peers trust their configured RPC for payments as well as bonds. Sellers rely on it for opening receipts, channel state, voucher checks, closure and broadcast; buyers rely on it for opening and top-up receipts and close evidence. A lying RPC cannot move funds, but it can lead a seller to serve unpaid requests, fake or hide a close, or censor recovery transactions.

Each wallet signs at most one unresolved transaction at a time, shared by channel opens, top-ups, closes, recovery, sends and bonds. Reconciliation runs on a 3-second tick, so a wallet lands roughly one transaction per tick. Requests on an existing channel need no transaction: vouchers and bills are off-chain, and the only chain work per request is the seller's read-only verification of a new or higher voucher; a request that presents the voucher the seller already stores needs none. A buyer therefore needs a transaction only for each new seller channel and each top-up; about 8 of them fit within the 25-second admission wait, so a buyer opening channels to many sellers at once should expect retries. A buyer runs any number of requests at once on its channel with a seller, one at a time per body. A seller lands about 1,200 closes per hour. It closes as soon as it sees a close request unless a request on that channel is running, which may delay the close by up to 600 seconds; that leaves at least 300 seconds, about 100 queued closes, before the buyer can withdraw, and a longer close backlog loses those captures. A seller watches its channels with one `eth_getLogs` query per tick for close requests, cancelled close requests and closes naming its payee, from a cursor stored in the ledger. The cursor moves only after a complete scan, and each scan reads the last 16 blocks again. The tick reads channel state only for channels named in those events, channels with a close request still pending (so the 600-second deferral is checked again every tick), closing channels and idle candidates. Every channel is read on the first tick, after a failed scan or a gap of more than 10,000 blocks, and at least every 120 seconds as a backstop against missing logs. These reads do not take the wallet's transaction slot. Opens and top-ups expire after 10 minutes; close and recovery attempts after one hour, so the default three retries outlast the buyer's earliest withdrawal during a fee spike, at the cost of a stuck attempt holding the slot for up to an hour. Other wallet calls, including voucher verification, serialize on the send lock and repeat the reserve ABI check.
